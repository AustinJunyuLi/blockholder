## Method notes

- All fetches went through `ego-browser` task space `lit-fetch-A`, inheriting the author's UCL-authenticated browser session (per the skill's cookie/session model).
- **Wiley** (JF, Econometrica): the reliable path is DOI → `/doi/epdf/<doi>` (confirms title + reveals the true `Download PDF` link) → `/doi/pdfdirect/<doi>?download=true`. This URL is same-origin and fetch()-able from a Wiley page context; PDFs under ~600KB could be fetched and base64-encoded in one `js()` call, larger ones needed the two-step pattern (fetch+store on `window`, then read back in ~150KB chunks) to avoid `Runtime.evaluate` timeouts.
- **OUP** (RFS): the `article-pdf` URL on `academic.oup.com` 302-redirects to a signed, time-limited URL on `watermark0N.silverchair.com` or `oup.silverchair-cdn.com`. That redirect target does **not** send CORS headers permitting `academic.oup.com`, so in-page `fetch()` always failed with `TypeError: Failed to fetch`. Also, direct browser *navigation* to the PDF opens Chrome's native PDF-viewer extension, which intercepts the response before `CDP Network.getResponseBody` can read real bytes (it only returns the tiny viewer-shell HTML). The reliable fix: enable `Fetch.enable` with `requestStage: 'Response'`, fire `Page.navigate` (or click the real link) without awaiting completion, drain events for the paused request(s) (continuing any non-terminal redirect hops), then call `Fetch.getResponseBody` on the actual PDF response and `Fetch.continueRequest` to release it. This CDP-level capture bypasses both the CORS block and the PDF-viewer interception, since it reads the body before the viewer ever gets it.
- Large/slow supplementary-data PDFs (Wiley `downloadSupplement`, OUP CDN appendix) needed extra wait time between the `Fetch.requestPaused` event and `Fetch.getResponseBody` (the response can still be streaming when the pause fires); ~8–10s worked reliably.
- Two DOIs given in the task brief were incorrect and resolved to unrelated papers (see kahn_winton_1998_jf and collin_dufresne_fos_2015_jf rows); both were corrected via a Crossref bibliographic-title lookup before fetching.
- No genuine login walls, captchas, or hard bot-blocks were hit and left unresolved. One transient Cloudflare interstitial (lmm_2026_internet_appendix) cleared on a normal retry without any bypass attempt. No target required manual user action.
- JSTOR and ScienceDirect were not touched (per instructions, known bot-blocked). SSRN was not needed as a fallback for any target.
